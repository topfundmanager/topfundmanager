# Glass Request reuse boundary

No Glass implementation or schema was modified. The existing Request email operations reference was read for compatibility, especially durable operations, explicit address ownership, participant threading, immutable retries, audit, and safe restores.

Reuse the small Gmail adapter and orchestration contracts, rather than copying the Top Fund Manager database. The UI uses application conversation/message UUIDs. A provider-normalized message contains `providerId`, `threadId`, `subject`, `date`, `from`, `to`, `cc`, `replyTo`, RFC `messageId`/`references`, plain-text `body`, state labels and attachment metadata; these IDs stay behind the application boundary. Attachment bytes are lazy and authorized. A mailbox is always scoped to an installation/workspace; optional site associations belong in a separate many-to-many relation.

Explicit capabilities are exported as `gmailCapabilities`: reply, reply-all, incoming attachments; no compose, forward, outgoing attachment, read-state mutation, delivery confirmation or provider send idempotency in this release. The adapter contract consists of `prepareSend()`, `sync()`, `watch()`, `stop()`, `send(immutablePayload)`, `reconcile(immutablePayload)`, and `attachment(providerMessageId, providerAttachmentId)`. Sync returns normalized changes and a proposed cursor/checkpoint, never directly commits it. Transport uses Google OAuth APIs and Pub/Sub rather than Resend receiving.

`EmailService(store, workspace, user)` expects a persistence interface with `query`, `one`, `write`, `upsert`, and named transactional `rpc` methods. `runJob(store, env, {adapter})` accepts an adapter factory; GmailAdapter accepts `fetcher` and `credentials` injections. The credential implementation must encrypt refresh tokens with installation/mailbox authenticated data and keep its key separate from persisted records. Jobs can be supplied by Glass's runner if they preserve atomic claim, mailbox serialization, lease fencing, immutable operations and crash-to-uncertain semantics. Replace the Top Fund Manager session/allowlist service and Cloudflare handlers with Glass authentication, installation grants, transport and scheduler.

Gmail owns threading via threadId plus matching subject and RFC reply headers. Do not apply Resend's plus-tag routing or merge subjects across mailboxes. Gmail primary identities need signed Workspace validation and per-mailbox consent; aliases need separately verified send-as capability before support. Groups are not OAuth mailboxes. Start with gmail.readonly + gmail.send and OpenID identity scopes; no domain-wide delegation.

Gmail acceptance is `sent`, not `delivered`. Resend's idempotency keys and delivery webhooks cannot be inherited. On an ambiguous Gmail call, reconcile with its stable RFC Message-ID in Sent before any operator decision. Never use a new operation ID to retry an uncertain send automatically. Bounces/delivery state and suppression policy would require separate Gmail-specific work; existing Request Resend semantics must remain provider-specific.

Remaining Glass work: choose installation ownership and mailbox grants; implement persistence/transaction adapters and credential settings; register client-owned Internal Google OAuth and authenticated Pub/Sub routing; connect Glass's drafts/attachments/status UI and audit; implement retention and restore controls; adapt the mocked and PostgreSQL contract tests; obtain approved test recipients and complete live Gmail/Request acceptance. Do not connect the existing Resend support address merely because its email string matches a Gmail account.
